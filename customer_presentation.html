1. Customer & Target Persona

Primary Customer: Global enterprises running mission-critical workloads (transactional processing, time-series engines, high-throughput caching, and AI inference pipelines) evaluating or executing architecture modernization from commodity x86 to IBM Power (ppc64le).

Target Personas:

  • IBM Infrastructure Sales & Technical Pre-Sales Specialists (Technical Sales Engineers / Solution Architects): Need to qualify migration feasibility, size porting timelines, and instill platform confidence during rapid competitive sales cycles.
  • Enterprise Architecture Decision-Makers (CIO / VP Infrastructure / Chief Architects): Require objective feasibility scoring, risk transparency, and effort bounds before committing to modernization proposals.
  • IBM Power Porting Lab & Ecosystem Engineers: Specialist teams who need structured transitive build-dependency specifications and reproducible toolchain requirements rather than vague application lists.

2. Business Problem & The Estimation Gap

While IBM Power delivers exceptional hardware throughput (massive memory bandwidth, SMT8 core threading, and built-in Matrix Math Accelerators), the pre-sales qualification process represents a major friction point:

  • Unstandardized & Heterogeneous Inputs: Customers submit dependency specifications across wildly disparate formats: CycloneDX/SPDX SBOMs, Dockerfiles, Python requirements files, or informal meeting notes.
  • Fragmented Ecosystem Registries: Probing package availability requires manual, time-consuming lookups across RHEL BaseOS, EPEL 9, Quay.io, Docker Hub, PyPI, and community repositories (Conda-forge, Open-CE).
  • The "Iceberg" Estimation Gap: When components lack prebuilt Power binaries, sales teams have no fast heuristic to look beneath the surface. Uncovered build-time dependencies (e.g. jemalloc needing 64KB page size tuning) or unported x86 SIMD intrinsics surface late, causing significant estimation variance and deal friction.

4. Proposed Opportunity & Agentic AI Solution

We designed and built the Autonomous IBM Power Porting Triage Agent—a lightweight, containerized platform that integrates deterministic multi-source probing with generative sales reasoning:

  • Universal Multi-Modal Ingestion: Automatically normalizes CycloneDX/SPDX SBOMs, Dockerfiles, Python requirements, raw text/emails, or direct GitHub repository / documentation URLs (e.g., https://github.com/facebook/rocksdb or https://rocksdb.org) by crawling repositories and inferring dependencies via Gemini LLM.
  • Deterministic Live Ecosystem Prober: Queries live API registries (Quay.io, Docker Hub v2, PyPI, RHEL/EPEL 9) to verify ppc64le multi-arch tags, returning canonical verification links directly to official package repositories.
  • Deep Transitive Build Dependency Analysis: Solves the iceberg problem by recursing through build trees to identify unported build-time requirements (BuildRequires, compiler toolchains, submodules).
  • Hardware Architecture Sensitivity Audit: Flags x86 SIMD/AVX2 intrinsics (prescribing SIMDe to Power VSX header mapping), 64KB memory page size risks (jemalloc alignment tuning), and inline assembly.
  • Single-Value Fibonacci Sizing Ceiling: Computes realistic person-days incorporating build requirements, SIMD adaptation, and test validation, mapped to the next Fibonacci number ceiling (e.g. 5→8 PD, 26→34 PD, 34→55 PD) to eliminate confusing ranges.
  • Positive Pre-Sales Qualification Tiers: Replaces negative traffic lights with positive, constructive tiers: Minimal Effort (Turnkey), Minor Effort, Moderate Effort, Significant Effort, and Not Possible As-Is (Alternative Required) with recommended drop-in substitutes.
  • 1-Click Executive PDF Generation: Generates high-fidelity, multi-page branded PDF feasibility memos ready for immediate delivery to client C-level executives.
